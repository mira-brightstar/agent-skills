# 流程蓝图：从想法到可维护的技能

> 项目：Skill 标准逆向工程 · 阶段 4 交付物
> 本文件是 14 步流程的详细说明。可执行定义以 `scripts/mentor/state.mjs` 与 `scripts/mentor/blueprint.mjs` 为准。
> 导师只查「流程走没走、产物有没有生成」；合规与质量评分交给包内的评定官。

## 0. 怎么用这份蓝图

```bash
# 看任意技能卡在第几步，以及该退回哪一步
node scripts/mentor/blueprint.mjs <repo-root> --scan skills --skill <name>

# 只看某一步或某个检查点
node scripts/mentor/blueprint.mjs <repo-root> --skill <name> --step STEP-03
node scripts/mentor/blueprint.mjs <repo-root> --skill <name> --checkpoint CP-1
```

输出会给出**第一个阻塞步骤**，而不是只给通过率。流程的价值在于告诉你下一步做什么。

## 2. 中间产物位置约定

| 位置 | 内容 | 是否随技能发布 |
|---|---|---|
| `design/<skill-name>/` | 过程记录：需求界定、生态决策、安全检查表（技能属于某仓库时） | 否（可选保留，作为设计档案） |
| `<skill-dir>/design/` | 同上（技能是独立目录、没有仓库根时） | 否 |
| `<skill-dir>/evals/` | 评测用例与基线 | **是**（质量模型检查这里） |
| `docs/<bucket>/<name>.md` | 人类文档页 | 是 |

这样切分的理由：**质量模型要检查的东西必须在技能目录内**，否则评分器找不到；
纯过程记录放在 `design/` 下，避免污染技能目录，也避免被打包分发。
检查器会自动尝试两种布局，独立技能无需伪造一个仓库根。

## 3. 逐步详解

### STEP-01 · 需求界定

**目标**：把「我想做个技能」变成「这个技能要解决哪个具体失败模式」，并明确不做什么。

**输入**

- 观察到的问题或反复出现的手工流程
- 现有技能清单（避免重复造轮子）

**动作**

- 写下它要消除的具体失败模式（不是「提升效率」这类空话）
- 写下触发场景：什么情况下应该用它
- 写下**不做什么**：明确划出范围外，防止技能膨胀
- 检索现有技能，确认没有重复（样本仓库用 ask-matt 这类路由技能做这件事）

**输出（中间产物）**

- `design/<name>/01-需求界定.md` ← 模板 `references/mentor/templates/01-需求界定.md`

**检查点**：需求界定文档存在，且含「失败模式 / 触发场景 / 不做的事」三节，每节非空

**自动验证**：文件 `design/<name>/01-需求界定.md` 存在且含小节 「失败模式」、「触发场景」、「不做的事」

**失败回退**：若「不做什么」写不出来，说明范围尚未收敛，不要进入 STEP-02。回到需求来源继续追问。

**关联条目**：—

### STEP-02 · 生态选择

**目标**：决定这个技能要跑在哪些 harness 上，并据此确定字段边界。

**输入**

- STEP-01 的需求界定文档

**动作**

- 选择目标生态：仅 Claude Code / Claude Code + Codex / 跨生态可移植
- 若需要 L1 字段（argument-hint、disable-model-invocation 等），写入 metadata.portability: claude-code-only
- 若只用 L0 六字段，写入 metadata.portability: portable
- 若声明支持 Codex，准备 agents/openai.yaml

**输出（中间产物）**

- `design/<name>/02-生态决策.md` ← 模板 `references/mentor/templates/02-生态决策.md`

**检查点**：frontmatter.metadata.portability 已显式取值（portable 或 claude-code-only）

**自动验证**：检查 `V-060`, `V-061` 全部通过

**失败回退**：若不确定是否需要 L1 字段，先按 portable 做（只用 L0 六字段）。后续要用 L1 字段时再改 portability，并同步补 agents/openai.yaml。

**关联条目**：`SPEC-060`、`SPEC-061`、`SPEC-062`

### STEP-03 · 接口设计

**目标**：在写实现之前，先定下五类契约——输入、输出、失败、副作用、依赖。

**输入**

- STEP-01 的需求界定文档
- STEP-02 的生态决策

**动作**

- 列出输入参数：每个参数的含义、缺省行为、非法输入的处理
- 确定输出形态：对话输出还是写文件；文件路径规则与格式
- 枚举失败模式 ≥2 类，每类给出明确行为；**禁止静默降级**
- 声明副作用类别，并区分可逆与不可逆
- 声明运行时依赖、外部服务、模型要求

**输出（中间产物）**

- `design/<name>/03-接口契约.yaml` ← 模板 `references/mentor/templates/03-接口契约.yaml`
- `<skill-dir>/SKILL.md（五段契约小节）` ← 模板 `evals/fixtures/release-notes/SKILL.md`（参考实现）

**检查点**：五段小节齐备：Inputs / Outputs / Failure modes / Side effects / Dependencies（内容为空时写「无」）

**自动验证**：检查 `V-040`, `V-042`, `V-043`, `V-045`, `V-050` 全部通过

**失败回退**：契约写不出来通常意味着实现细节还没想清。允许先写「待定」并在 STEP-06 回填，但**不允许删除小节**——小节存在性本身是检查项。

**关联条目**：`SPEC-040`、`SPEC-041`、`SPEC-042`、`SPEC-043`、`SPEC-045`、`SPEC-050`、`QM-FN-L3`、`QM-RB-L3`、`QM-SC-L3`

### STEP-04 · 目录初始化

**目标**：建立技能目录骨架，确保生态能正确发现它。

**输入**

- STEP-02 的生态决策
- 技能名（kebab-case）

**动作**

- 创建目录 <bucket>/<skill-name>/
- 创建 SKILL.md，第一行必须是 ---
- 按需创建可选目录：scripts/（可执行）、references/（按需读）、assets/（静态资源）
- 若支持 Codex，创建 agents/openai.yaml

**输出（中间产物）**

- `<skill-dir>/SKILL.md` ← 模板 `evals/fixtures/release-notes/SKILL.md`（参考实现）

**检查点**：目录名合法（^[a-z0-9]+(-[a-z0-9]+)*$）、SKILL.md 存在且首行为 ---、frontmatter 可解析

**自动验证**：检查 `V-001`, `V-002`, `V-003`, `V-004` 全部通过

**失败回退**：若 frontmatter 解析为空（V-004 失败），通常是首行有 BOM 或空行，或 YAML 缩进用了 Tab。用 claude plugin validate 或本工具定位。

**关联条目**：`SPEC-001`、`SPEC-002`、`SPEC-003`、`SPEC-004`、`SPEC-005`、`SPEC-006`、`QM-FN-L1`

### STEP-05 · 元数据

**目标**：填写 frontmatter，使技能可被正确发现、触发、分发。

**输入**

- STEP-02 的生态决策
- STEP-01 的需求界定（用于写 description）

**动作**

- name：必须等于目录名
- description：说明「做什么」+「何时用」，≤1024 字符
- portability：与 STEP-02 一致
- compatibility：环境要求与依赖（≤500 字符）
- allowed-tools：若声明，必须最小权限并说明理由；Bash 系工具必须收窄作用域
- 触发方式：model-invoked（默认）或 user-invoked（同时设 disable-model-invocation 与 openai.yaml 的 policy）

**输出（中间产物）**

- `<skill-dir>/SKILL.md（frontmatter）` ← 模板 `evals/fixtures/release-notes/SKILL.md`（参考实现）

**检查点**：name == 目录名、description 合法、字段全部在白名单内、portability 正确、触发方式跨生态一致

**自动验证**：检查 `V-010`, `V-011`, `V-014`, `V-015`, `V-016`, `V-017`, `V-021`, `V-031`, `V-061` 全部通过

**失败回退**：若 V-014（未知字段）失败：字段名拼错会被**静默忽略**，技能能跑但行为不符预期。逐字对照 references/assessor/schema 里的字段表。

**关联条目**：`SPEC-010`、`SPEC-011`、`SPEC-014`、`SPEC-015`、`SPEC-016`、`SPEC-017`、`SPEC-020`、`SPEC-021`、`SPEC-031`、`SPEC-033`、`QM-DC-L1`、`QM-SC-L4`

### STEP-06 · 实现

**目标**：写出技能正文——让模型照着做能稳定得到预期结果。

**输入**

- STEP-03 的接口契约
- 领域词汇表（如 CONTEXT.md）

**动作**

- 写步骤，每步带可观察的完成判据
- 深层材料外置到 references/，保持 SKILL.md ≤500 行（渐进披露）
- 引用其他技能用「Call the Skill tool with X」，不用跨目录文件路径
- 若技能有副作用，明确写出确认点

**输出（中间产物）**

- `<skill-dir>/SKILL.md（正文）` ← 模板 `evals/fixtures/release-notes/SKILL.md`（参考实现）

**检查点**：正文自包含（无跨目录引用）、体量受控（≤500 行）、引用不超过一层

**自动验证**：检查 `QM-MT-L2`, `QM-MT-L4` 全部通过

**失败回退**：若正文超过 500 行：把「参考材料」搬到 references/，主文件只留决策与步骤。注意别把步骤本身也搬走——步骤是常驻指令，不是参考资料。

**关联条目**：`SPEC-007`、`SPEC-052`、`QM-FN-L2`、`QM-MT-L2`、`QM-MT-L4`

### STEP-07 · 测试

**目标**：写出评测用例，让「改动之后怎么知道没坏」有确定答案。

**输入**

- STEP-03 的接口契约（失败模式即用例来源）

**动作**

- 为每个失败模式写 ≥1 个用例
- 用例含三段：输入情境（case）、期望行为断言（expect）、失败反例（fail case）
- 用例放在 <skill-dir>/evals/

**输出（中间产物）**

- `<skill-dir>/evals/*.yaml` ← 模板 `references/mentor/templates/07-评测用例.yaml`

**检查点**：evals/ 下存在含 case / expect 字段的用例文件

**自动验证**：检查 `QM-TS-L2b`, `QM-TS-L3` 全部通过

**失败回退**：若写不出用例，说明 STEP-03 的失败模式写得不够具体。退回 STEP-03，把「失败模式」改写成可观察的行为描述。

**关联条目**：`QM-TS-L2`、`QM-TS-L2b`、`QM-TS-L3`

### STEP-08 · 文档

**目标**：写出人类文档页，让使用者不必读 SKILL.md 就能判断「要不要用它」。

**输入**

- STEP-01 的需求界定
- STEP-03 的接口契约

**动作**

- 创建 docs/<bucket>/<name>.md
- 含固定四段：What it does / When to reach for it / Common questions / It's working if
- 链接使用绝对路径，不写仓库相对路径；不写安装命令；不署名

**输出（中间产物）**

- `docs/<bucket>/<name>.md`

**检查点**：文档页存在且四段标题齐备

**自动验证**：检查 `C-11`, `C-12` 全部通过

**失败回退**：若「Common questions」写不出来，去 issue / changelog / 真实提问里找，不要编造。样本仓库的 wait-what.md 就漏了这一节（真实漂移案例）。

**关联条目**：`SPEC-066`、`QM-DC-L3b`

### STEP-09 · 示例

**目标**：给出至少一个真实示例，让使用者与模型都能对齐预期。

**输入**

- STEP-07 的评测用例（可复用为示例）

**动作**

- 写 1 个「输入 → 输出」的真实示例（不是伪代码）
- 示例可放在 SKILL.md 正文，也可放在 references/ 或文档页
- 示例必须与技能实际行为一致（否则会误导）

**输出（中间产物）**

- `<skill-dir>/references/ 或 SKILL.md 内的示例小节`

**检查点**：技能内或文档页存在 ≥1 个真实示例（代码块或示例小节）

**自动验证**：检查 `QM-FN-L2b`, `QM-DC-L4` 全部通过

**失败回退**：示例与实现不一致时，**改实现而不是改示例**——除非能证明示例才是预期行为。

**关联条目**：`QM-FN-L2b`、`QM-DC-L4`

### STEP-10 · 评测

**目标**：实际跑一遍评测并留下基线，使后续改动可回归对比。

**输入**

- STEP-07 的评测用例

**动作**

- 写一个可执行运行器（scripts/ 或 evals/ 下），返回非零退出码表示失败
- 跑一遍并记录基线结果
- 把评测接入 CI 门禁

**输出（中间产物）**

- `<skill-dir>/evals/ 运行器 + BASELINE.md`

**检查点**：存在可执行运行器、≥1 个失败路径用例、CI 配置中含评测步骤

**自动验证**：检查 `QM-TS-L4` 全部通过

**失败回退**：若无法自动化（需要人工判断输出好坏），降级为「结构化人工检查表」并声明为 manual，但必须在文档中写清人工判定标准。

**关联条目**：`QM-TS-L4`、`QM-TS-L5`

### STEP-11 · 安全合规

**目标**：在发布前确认技能不会越权、不会泄露、不会成为注入载体。

**输入**

- STEP-03 的副作用声明
- STEP-05 的 allowed-tools

**动作**

- 扫描硬编码凭证（占位符除外）
- 确认 allowed-tools 最小权限，Bash 系工具已收窄作用域
- 确认不可逆操作有显式确认
- 确认技能不把外部内容当指令执行（提示注入）
- 声明数据处理边界：哪些数据会发往哪个外部端点
- 若携带脚本：有 shebang、有错误信息、不依赖隐式环境

**输出（中间产物）**

- `design/<name>/11-安全合规检查表.md` ← 模板 `references/mentor/templates/11-安全合规检查表.md`

**检查点**：无硬编码凭证、Bash 系工具已收窄、副作用已声明、不可逆操作有确认

**自动验证**：检查 `V-070`, `V-071`, `V-021`, `V-045` 全部通过

**失败回退**：若某项无法满足（例如确实需要宽泛的 Bash 权限），必须在 compatibility 中说明理由并标注为已知风险，不能默默放行。

**关联条目**：`SPEC-020`、`SPEC-021`、`SPEC-046`、`SPEC-070`、`SPEC-071`、`SPEC-072`、`SPEC-073`、`SPEC-074`、`QM-SC-L2`、`QM-SC-L3`、`QM-SC-L4`、`QM-SC-L5`

### STEP-12 · 打包

**目标**：把技能登记进分发清单，确保能被安装且不会泄漏半成品。

**输入**

- STEP-04~11 的全部产物

**动作**

- 在分发清单（如 .claude-plugin/plugin.json 的 skills 数组）登记
- 在顶层 README 中链接到 SKILL.md
- 确认未发布技能（in-progress/misc）不出现在清单与 README 中
- 确认清单无悬空路径

**输出（中间产物）**

- `分发清单 + README.md`

**检查点**：清单与实际目录双向对齐：无悬空、无漏登、无未发布项泄漏

**自动验证**：检查 `C-05`, `C-06`, `C-07`, `C-08` 全部通过

**失败回退**：清单悬空会导致**插件安装失败**（整个插件不可用，不只是这个技能）。发布前务必跑 audit.mjs。

**关联条目**：`SPEC-063`、`SPEC-065`、`QM-MT-L3`

### STEP-13 · 发布

**目标**：打版本、写变更记录，让使用者知道改了什么。

**输入**

- STEP-12 的打包结果

**动作**

- 更新版本号（单一真相源，多清单必须一致）
- 写变更记录（CHANGELOG 或 changeset）
- 确认技能内 L1 字段的可移植性声明仍然正确

**输出（中间产物）**

- `CHANGELOG.md 或 .changeset/*.md`

**检查点**：版本号多清单一致；存在变更记录

**自动验证**：检查 `C-15` 全部通过

**失败回退**：版本漂移会让更新不可复现。用 --check 模式（如 sync-plugin-version.mjs --check）在 CI 中拦住它。

**关联条目**：`SPEC-064`、`QM-DC-L5`

### STEP-14 · 维护

**目标**：让技能在三个月后仍然可改、可弃。

**输入**

- 已发布的技能
- 使用反馈

**动作**

- 声明 owner / 维护者
- 建立废弃策略：弃用时如何通知、是否保留替代者指引
- 保持评测用例与行为变更同步
- 定期重跑评测与质量评分，跟踪等级变化

**输出（中间产物）**

- `CODEOWNERS 或 metadata.owner + 废弃约定`

**检查点**：存在 owner 声明与废弃约定；评测随行为变更同步更新

**自动验证**：检查 `QM-MT-L5`, `QM-TS-L5` 全部通过

**失败回退**：技能无人维护时，应移入 deprecated 并从分发清单移除，而不是留在原地腐化。样本仓库用 skills/deprecated/ 承载这一状态。

**关联条目**：`SPEC-065`、`QM-MT-L5`、`QM-TS-L5`

## 4. 设计说明：为什么是这十四步

| 设计取舍 | 理由 |
|---|---|
| **接口设计（STEP-03）在实现（STEP-06）之前** | 契约写不出来通常意味着实现细节还没想清。先写契约能提前暴露这个信号，而不是写完 200 行才发现失败模式说不清。 |
| **测试（STEP-07）在文档（STEP-08）之前** | 失败模式是评测用例的来源，而评测用例又可以是示例的来源。先有测试再写文档，文档才不会沦为营销文案。 |
| **安全合规（STEP-11）在打包（STEP-12）之前** | 打包之后技能就可被安装，安全审查必须在它可被分发之前完成。 |
| **每步都有失败回退，且多数回退指向**前**一步** | 流程卡住时最常见的错误是「在当前位置硬撑」。回退到上游修正，比在下游打补丁便宜得多。 |
| **低级别步骤不设无效约束** | STEP-01~04 的门槛刻意保持宽松（写文档、建目录），把严格约束集中在 STEP-05 之后。约束太早会压制探索。 |

## 5. 与 SPEC / QM 的关系

| | SPEC | QM | 流程蓝图 |
|---|---|---|---|
| 回答 | 合法吗 | 多成熟 | **怎么做出来** |
| 形态 | 二值门禁 | 分级评分 | 有序步骤 + 回退路径 |
| 使用时机 | 发布前 | 评审时 | 创建时 |

不另造判定逻辑。这样修正检查器时，三份产物同步受益。
