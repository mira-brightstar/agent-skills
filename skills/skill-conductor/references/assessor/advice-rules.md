# 问题表述规则（用户报告）

> 本文件规定「怎么把内部判定写成用户能看懂的问题」。判定口径见 `spec.md` 与 `quality-model.md`；输出禁用词见 `agent-runbook.md` 第 7 节。

## 1. 每条问题的固定结构

| 字段 | 要求 |
|---|---|
| 标题 | 一句话说清缺什么或错在哪，不用内部代号 |
| 位置 | 文件 + 小节；不写绝对路径；没有可靠行号就不写行号 |
| 现状 | 具体缺失、冲突或证据；不写「可能」「大概」 |
| 影响 | 对使用者或维护者的后果 |
| 建议 | 可直接照做的修改；必要时给 3~5 行骨架 |
| 证据 | 具体文件/小节/摘录；没有证据就不写这条问题 |
| 置信度 | 确定 / 较确定 / 需复核 |

## 2. 分级与优先级

| 级别 | 来源 | 写法 |
|---|---|---|
| 阻断 | `validate` / `audit` 的 MUST 失败 | 不修不能发布；放「阻断问题」；置信度「确定」 |
| 重要 | `score` 瓶颈中的具体缺陷；软轨工程 `fail` + `high` | 影响可用性/可维护性；放「重要问题」 |
| 建议 | `audit` SHOULD；软轨工程 `fail` + `medium`；文风 `needsFix`；其余已确认的机器缺陷（如无变更记录/无 owner） | 审计类放「建议改进」，文风类放「文风」；纯风格项标「低（风格项）」 |
| 内容质量 | 软轨 `group=content` 的 `fail` | 放「内容质量」，不并入工程问题 |
| 不写入 | `low`、`pending`、无证据的猜测 | 不进入用户报告 |

## 3. 合并规则

- 同一根因只写一条。五个契约小节缺失 → 一条「缺少输入、输出和边界说明」，在「现状」里列出五节。
- 同一问题不要同时出现在两个章节。
- 一个建议只对应一个动作；不要把「补文档 + 补测试 + 改权限」塞成一句话。
- 软轨内容条目只进「内容质量」；工程条目只进「阻断 / 重要 / 建议」。

## 4. 常见问题对照

第一列是内部信号，只用于定位；写报告时只用后五列。

| 内部信号 | 用户标题 | 现状要点 | 影响 | 建议要点 | 优先级 / 置信度 |
|---|---|---|---|---|---|
| `V-040/042/043/045/050`、`QM-DC-L3` | 缺少输入、输出和边界说明 | 没有 Inputs / Outputs / Failure modes / Side effects / Dependencies 小节 | 使用者不知道要提供什么、出错时怎么办、会不会写文件 | 补齐五节；每节写含义、缺省值、非法值、可逆性；内容为空写「无」 | 阻断 / 确定 |
| `C-13`（仅声明支持 Codex/OpenAI 时） | 声明支持 Codex/OpenAI 但缺少接口文件 | 技能目录没有 `agents/openai.yaml`，且正文/compatibility 提到 Codex/OpenAI | 在 Codex/OpenAI 中无法显示名称与简介，也无法声明是否允许自动调用 | 新增该文件，填 `display_name`、25~64 字符的 `short_description`、`policy.allow_implicit_invocation`；若只在 TRAE/通用生态使用，可不补 | 阻断（仅声明时）/ 确定 |
| `C-13`（未声明时） | 未声明 Codex/OpenAI 支持 | 没有 `agents/openai.yaml`，正文也未提到 Codex/OpenAI | 当前生态不需要该文件；若未来要在 Codex/OpenAI 分发，会缺 UI 元数据 | 报告中写「平台适配：未声明 Codex/OpenAI，不要求接口文件」；不列为问题 | 不写入 / 确定 |
| `V-075` | 随包大体积数据缺少授权说明 | 有 >2MB 数据文件，但没有 `LICENSE`/许可/授权声明 | 版权与分发范围不清，公开分发有风险 | 加 `LICENSE` 或授权说明；不需要随包时移出技能目录；授权范围需人工确认 | 中（合规）/ 确定（文件事实），授权范围需复核 |
| `V-076` | 技能文本包含本机绝对路径 | 正文或引用文件出现盘符路径、Unix 用户目录 | 泄露本机目录结构或用户名 | 改为相对路径、`<技能目录>` 或 `~/...` 占位符 | 低（隐私）/ 确定 |
| `V-077` | 副作用未声明读取范围 | Side effects 小节没有说明读哪些目录/文件，也没有写「不读取」 | 用户不知道技能会读哪些文件 | 在 Side effects 写明读取目录/文件；纯文本输出写「不读取」；若 Side effects 已缺失，合并到「缺少输入、输出和边界说明」，不单列 | 中（安全）/ 确定 |
| `QM-TS-L2b`、`QM-TS-L3`、`QM-TS-L4` | 无法验证和回归 | 没有 Verification 小节、没有评测用例、没有可执行运行器或 CI 步骤 | 改动后无法判断是否破坏原有行为 | 加 `## Verification` 写可观察判据；加 3 个 `case` + `expect`；加运行器并接入 CI | 高（可验证）/ 确定 |
| `QM-FN-L2b`、`QM-DC-L4` | 没有可照着做的示例 | 正文与引用文件都没有「输入 → 输出」示例 | 新用户不知道输出长什么样，模型也缺少对齐样本 | 加 1 个真实示例（≥5 行），并与评测用例保持一致 | 高（可用性）/ 确定 |
| `QM-FN-L4` | 没有回归基线 | 没有 `evals/` 或 `tests/` 下的「输入 + 期望」对 | 无法判断改动是否破坏行为 | 把示例与失败模式写成可执行用例 | 高（可验证）/ 确定 |
| `QM-MT-L5` | 没有维护者信息 | 没有 `metadata.owner` 或 `CODEOWNERS` | 出问题找不到负责人，弃用时无人通知 | 加 owner；写明弃用通知方式与保留期 | 中（维护）/ 确定 |
| `QM-DC-L5` | 没有变更记录 | 没有 `CHANGELOG.md`，评测里也没有 `history` | 行为变化无法追溯 | 加变更记录，或在一个评测文件里维护 `history` | 中（维护）/ 确定 |
| `QM-RB-L3`、`QM-SC-L3` | 失败与副作用未声明 | 缺 Failure modes 或 Side effects | 出错时行为不可预期；写操作可能覆盖用户文件 | 至少写 2 类失败（触发 → 行为 → 退出方式）；逐项标注可逆/不可逆 | 阻断 / 确定 |
| `C-16` | 标点与仓库规范不一致 | 正文含英文长破折号 | 与仓库风格不一致 | 替换为中文标点；若目标仓库没有此规范，可注明忽略 | 低（风格项）/ 确定 |
| 软轨 `group=quality` `fail` | 按该条目的 `reason` / `evidence` 写具体标题 | 引用实际证据，不写检查 ID | 按证据说明后果 | 按锚点的「反例 → 正例」给改法 | `high` → 重要 / 较确定；`medium` → 建议 / 需复核 |
| 软轨 `group=content` `fail` | 放进「内容质量」，不放进工程问题 | 引用原文与证据 | 说明内容层面的缺口 | 按 CQ 条目的正例给改法 | `high` → 较确定；`medium` → 需复核 |
| 文风 `needsFix` | 放进「文风」章节，不放进问题清单 | 引用原文与改文 | 说明读起来哪里卡住 | 给针对原文的改法或改写方向 | 低（文风）/ 按置信度 |

## 5. 输出约束

- 不写检查 ID、脚本名、退出码、JSON 字段；完整禁用词见 `agent-runbook.md` 第 7 节。
- 不写绝对路径；证据里出现本机路径时脱敏为 `<本机路径>`。
- 不编造行号、原文、文件内容或未读过的证据。
- 内容质量未评审时，不评价内容深度、原创性、自洽性；文风未评审时，不评价文笔、措辞、节奏或风格。
- 不写「已跳过」「pending」「参考信号」。
