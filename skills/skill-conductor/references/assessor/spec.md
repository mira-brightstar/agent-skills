> 项目：Skill 标准逆向工程 · 阶段 2 交付物
> 版本：v1.0（条目编号保持稳定；包的契约版本见 `SKILL.md` 的 `metadata.contract-version`）
> 条目编号：`SPEC-001` ~ `SPEC-077`（分段预留，便于后续插入）
> 证据基础：阶段 1 生态解剖报告（历史材料，未随包分发）

## 0. 定位与设计约束

### 0.1 本规范要解决的问题

生态现状（【已验证】，见阶段 1 报告）：

- 跨生态规范 `agentskills.io/specification` 已存在，但**只定义了 6 个字段**，覆盖不到触发方式、接口、依赖、安全。
- Claude Code 扩展了 14 个字段，但这些字段**跨生态不可移植**，越界时在 claude.ai 上传会**硬报错**、在 CC 内却**静默忽略**。
- 三个维度的契约在生态中**完全空白**：输入/输出契约、错误契约、副作用声明。
- 已有社区工具（`skill-linter` 47 规则、`skillspec-check` L1/L2/L3 分级）在做 lint 与分级。

→ 因此本规范的差异化定位是：**分级门槛可辩护 + 豁免机制明确 + 不可机器判定处给专家锚点 + 用一致性验证（kappa）保证结论稳定**。

### 0.2 三条硬设计约束

| 约束 | 含义 | 落实方式 |
|---|---|---|
| **MUST 只覆盖三件事** | 互操作 / 安全 / 可复现 | 每条 SPEC 的「维度」列只能是这三者之一 |
| **每条必须可观察、可复现、有阈值** | 不接受形容词式要求 | 每条必须有「阈值/命令」与「失败样貌」 |
| **豁免必须显式** | 不能默默不遵守 | 每条有「豁免」列，写 `无` 或具体豁免条件 |

### 0.3 维度定义

| 维度 | 定义 | 举例 |
|---|---|---|
| **互操作** | 技能能被目标生态正确加载、发现、触发、分发 | 字段名合法、清单对齐、跨生态语义一致 |
| **安全** | 技能不会越权、不会静默造成不可逆损害、不会成为注入载体 | 最小权限、副作用声明、不可逆确认 |
| **可复现** | 换一个人/一台机器/一个时间点，得到相同结论 | 版本单一真相源、依赖声明、失败模式明确 |

### 0.4 质量等级定义（与阶段 3 质量模型共用）

「起始级别」= 该条要求**从哪个等级开始强制**。低于该等级时不检查、不扣分。

| 级别 | 名称 | 判据（一句话） | 典型场景 |
|---|---|---|---|
| **L1** | Demo 级 | 能在自己的机器上跑起来 | 个人实验、验证想法 |
| **L2** | 可用级 | 换个人也能用，不需要问作者 | 小范围分享、内部试用 |
| **L3** | 团队级 | 团队共享，改动不会破坏别人 | 团队仓库、内部工具集 |
| **L4** | 生产级 | 生产环境依赖它，出问题要能定位 | 产品线使用、对外分发 |
| **L5** | 关键生产级 | 关键路径，事故代价不可接受 | 涉及资金/数据/合规 |

## 1. 分层模型（本规范的核心结构）

技能的可移植性不是二元的，而是四层。**层决定强制力**：

```
┌─────────────────────────────────────────────────────────────┐
│  L3 仓库层 (Repo/Registry)      SHOULD    分发与治理          │
│  plugin.json · marketplace.json · docs/ · CHANGELOG.md      │
├─────────────────────────────────────────────────────────────┤
│  L2 适配层 (Codex)              SHOULD    声明支持时才强制    │
│  agents/openai.yaml                                          │
├─────────────────────────────────────────────────────────────┤
│  L1 扩展层 (Claude Code)        MAY       必须声明边界        │
│  14 个 CC 专有 frontmatter 字段                              │
├─────────────────────────────────────────────────────────────┤
│  L0 中立内核 (Core)             MUST      跨生态可移植        │
│  6 字段 + 目录结构                                            │
│  name · description · license · compatibility ·              │
│  metadata · allowed-tools                                    │
└─────────────────────────────────────────────────────────────┘
```

### 1.1 字段归属总表

| 层 | 字段 | 强制力 | 依据 | 可信度 |
|---|---|---|---|---|
| **L0** | `name` | MUST | spec「Required: Yes」 | 【已验证】E-09 |
| **L0** | `description` | MUST | spec「Required: Yes」 | 【已验证】E-09 |
| **L0** | `license` | MAY | spec 可选；CC 接受但不生效 | 【已验证】E-10 |
| **L0** | `compatibility` | MAY | spec 可选，≤500 字符 | 【已验证】E-09 |
| **L0** | `metadata` | MAY | spec 可选，string→string | 【已验证】E-09 |
| **L0** | `allowed-tools` | MAY（但声明即受安全约束） | spec 标记 Experimental | 【已验证】E-09 |
| **L1** | `when_to_use` | MAY | CC 专有 | 【已验证】E-10 |
| **L1** | `argument-hint` | MAY | CC 专有 | 【已验证】E-10 |
| **L1** | `arguments` | MAY | CC 专有 | 【已验证】E-10 |
| **L1** | `disable-model-invocation` | MAY | CC 专有 | 【已验证】E-10 |
| **L1** | `user-invocable` | MAY | CC 专有 | 【已验证】E-10 |
| **L1** | `disallowed-tools` | MAY | CC 专有 | 【已验证】E-10 |
| **L1** | `model` / `effort` | MAY | CC 专有 | 【已验证】E-10 |
| **L1** | `context` / `agent` / `background` | MAY | CC 专有 | 【已验证】E-10 |
| **L1** | `hooks` / `paths` / `shell` | MAY | CC 专有 | 【已验证】E-10 |
| **L2** | `interface.display_name` | SHOULD | openai/skills 仓库代码 | 【二手】E-18 |
| **L2** | `interface.short_description` | SHOULD | 同上，25-64 字符 | 【二手】E-18 |
| **L2** | `policy.allow_implicit_invocation` | SHOULD | 同上 | 【二手】E-18 |
| **L3** | `plugin.json` 字段 | SHOULD | 官方 schema 存在 | 【已验证】E-08 |

### 1.2 关键推论

1. **L0 是唯一可以定 MUST 的元数据层。** L1/L2 的依据强度不足（L2 甚至未进官方文档页），把它们定为 MUST 会让标准建立在非公开契约上。
2. **使用 L1 字段不是错误，不声明才是错误。** 因为 L1 字段会让技能在 claude.ai/Skills API 路径上**硬报错**（E-12），所以必须显式声明可移植性边界。
3. **L3 是"分发"而非"技能"的规范。** 单个技能可以完全没有 L3，但如果要发布，L3 强制力上升。

## 2. 规范条目

### 2.A 结构与命名

| ID | 维度 | 起始级别 | 强制力 | 要求 | 验证方式 | 阈值 / 命令 | 证据 | 豁免 | 失败样貌 |
|---|---|---|---|---|---|---|---|---|---|
| **SPEC-001** | 互操作 | L1 | **MUST** | 技能必须是一个目录，目录内必须含 `SKILL.md` | 机器 | `test -f <skill>/SKILL.md` | E-09 | 无 | 目录被生态忽略，技能不存在 |
| **SPEC-002** | 互操作 | L1 | **MUST** | 目录名必须匹配 `^[a-z0-9]+(-[a-z0-9]+)*$`，长度 1–64 | 机器 | 正则 + `len()` | E-09（spec 含反例） | 无 | 打包/上传被拒；跨生态命令名不可用 |
| **SPEC-003** | 互操作 | L1 | **MUST** | `SKILL.md` 的**第一行**必须是 `---` | 机器 | 首行严格比对 | E-11（S-03） | 无 | 整个 frontmatter 被当作正文，元数据全空 |
| **SPEC-004** | 互操作 | L1 | **MUST** | frontmatter 必须是合法 YAML，且由一行 `---` 闭合 | 机器 | YAML 解析器 | E-11（S-02） | 无 | 技能能加载但**所有字段为空**，自动触发失效 |
| **SPEC-005** | 可复现 | L2 | SHOULD | 可选目录使用固定语义：`scripts/`（可执行）、`references/`（按需读）、`assets/`（静态资源） | 机器 | 目录名白名单 | E-09 | 已有其他组织方式且文档已说明 | 同一仓库内布局不一致（阶段 1 观测到 12 种变体） |
| **SPEC-006** | 可复现 | L1 | MAY | 允许任意附加文件与目录（不得用白名单限制） | 机器 | 无限制 | E-09 | — | 过度限制会误杀合法设计 |
| **SPEC-007** | 互操作 | L2 | SHOULD | 引用其他文件必须用相对技能根的路径，且**一层深**，不得形成引用链 | 机器 | 解析 Markdown 链接，深度 ≤1 | E-09 | 无 | 深层引用链导致上下文爆炸或文件找不到 |

**SPEC-003 / SPEC-004 为什么是 MUST**：它们对应的失败是**静默的**（不报错、不崩溃，只让技能悄悄失效）。可复现性被破坏而无任何信号，是质量事故最隐蔽的来源。

### 2.B 元数据字段

| ID | 维度 | 起始级别 | 强制力 | 要求 | 验证方式 | 阈值 / 命令 | 证据 | 豁免 | 失败样貌 |
|---|---|---|---|---|---|---|---|---|---|
| **SPEC-010** | 互操作 | L1 | **MUST** | frontmatter 必须含 `name`，且值**必须等于**目录名 | 机器 | 字符串相等 | E-09 | 无 | 跨生态打包硬报错；Skill 工具调用名错位 |
| **SPEC-011** | 互操作 | L1 | **MUST** | frontmatter 必须含 `description`，非空，1–1024 字符 | 机器 | `1 <= len <= 1024` | E-09 | 无 | 模型无法自动触发该技能 |
| **SPEC-012** | 互操作 | L2 | SHOULD | `description` 必须同时说明「做什么」与「何时用」 | 专家 | 见 §4.1 锚点 | E-09 | 用户触发型技能（面向人，只需「做什么」） | 技能要么不触发，要么到处误触发 |
| **SPEC-013** | 互操作 | L3 | SHOULD | `description` + `when_to_use` 合并文本 ≤1536 字符 | 机器 | `len(desc) + len(when_to_use) <= 1536` | E-14 | 无 | 列表中被截断，后半段触发词失效 |
| **SPEC-014** | 互操作 | L1 | **MUST** | 字段名必须来自 §1.1 白名单；出现未知字段即视为错误 | 机器 | 集合比对 | E-11（S-01） | 无 | 字段被**静默忽略**，作者以为生效了 |
| **SPEC-015** | 互操作 | L1 | **MUST** | 字段名必须为小写连字符形式；唯一例外 `when_to_use` | 机器 | 正则 `^[a-z][a-z0-9-]*$` | E-10 | 无 | 拼错（如 `disableModelInvocation`）被静默忽略 |
| **SPEC-016** | 可复现 | L4 | **MUST** | `metadata` 必须是 `string → string` 映射；禁止嵌套对象或数组 | 机器 | YAML 类型校验 | E-09、E-15 | 无 | 严格实现下打包失败；工具读取到非预期类型 |
| **SPEC-017** | 可复现 | L4 | **MUST** | `metadata` 的键不得复用 frontmatter 字段名 | 机器 | 键与白名单交集为空 | E-10（官方明文告诫） | 无 | 与官方字段语义冲突，未来升级时行为不可预测 |
| **SPEC-018** | 互操作 | L3 | MAY | `license` 可声明许可（CC 接受但不生效） | 机器 | 非空字符串 | E-10 | — | 使用者无法判断授权范围 |
| **SPEC-019** | 互操作 | L3 | MAY | `compatibility` 可声明环境要求，≤500 字符 | 机器 | `len <= 500` | E-09 | — | 环境不满足时无预警 |
| **SPEC-020** | 安全 | L4 | SHOULD | 声明 `allowed-tools` 时必须在 `compatibility` 或正文中说明**为何需要** | 专家 | 见 §4.2 锚点 | E-13 | 无 | 审阅者无法判断权限是否最小 |
| **SPEC-021** | 安全 | L4 | SHOULD | `allowed-tools` 中的 **Bash 系工具**必须收窄作用域，禁止裸名 | 机器 | 出现裸 `Bash`/`PowerShell`/`Execute` 即失败 | E-13 | Read/Write/Edit 等**无文档化作用域语法**的工具可用裸名 | 技能自我授予无限制命令执行权限 |
| **SPEC-022** | 互操作 | L3 | MAY | `disallowed-tools` 可用于自主技能禁用交互类工具 | 机器 | 字段存在性 | E-10 | — | 后台循环技能弹出提问阻塞执行 |

> **SPEC-021 的安全依据**：官方原文「Workspace trust doesn't gate this field… A skill can grant itself broad tool access」【已验证】E-13。裸 `Bash` 等于无限制命令执行，且**在未受信目录也生效**。

## 3. 契约的落地方式（重要）

生态没有为「接口契约」提供字段，所以本规范用**两段式落地**，避免创造不可机器读取的自定义字段：

### 3.1 机器可读部分 → 用 L0 的 `compatibility` + `metadata`

```yaml
compatibility: "需要 git 与 gh CLI；读文件、写文件；单轮内完成；无需网络"
metadata:
  contract-version: "1"
  portability: "claude-code-only"
  side-effects: "read-files,write-files"
  failure-modes: "no-merge-base,gh-unauthenticated,empty-range"
```

- `compatibility` 承载**环境与依赖**（spec 原生语义）。
- `metadata` 承载**结构化契约**（spec 允许任意 string→string 扩展位）。
- 键名不得与 frontmatter 字段冲突（SPEC-017）。

**保留键（本规范定义）**：

| metadata 键 | 取值 | 对应条目 |
|---|---|---|
| `portability` | `portable` \| `claude-code-only` | SPEC-060 / SPEC-061 |
| `contract-version` | 本规范版本号 | 用于未来契约演进 |
| `side-effects` | 逗号分隔的副作用类别 | SPEC-045 的机器可读形式 |
| `failure-modes` | 逗号分隔的失败模式标识 | SPEC-043 的机器可读形式 |

### 3.1.1 为什么 `portability` 用显式标记而不是散文声明（一次真实的粒度修正）

本条在实现过程中被修正过一次，记录如下，因为它直接演示了本项目的核心难点：

| 版本 | 做法 | 回测结果 | 问题 |
|---|---|---|---|
| v1 | 要求技能正文用自然语言声明「仅 Claude Code 生效」 | 样本仓库 22/38 失败 | 仓库级事实被要求重复 22 遍，属**过细压制** |
| v1.1 | 改为「技能内 **或** 仓库级散文声明」 | 仓库级检测漏检（正则匹配不到样本实际措辞） | 用**自然语言匹配做判定**，违反 A-08 原则 |
| **v2（现行）** | 要求 `metadata.portability: "claude-code-only"` 显式标记 | 判定零歧义、可完全自动化 | 代价是每技能多一行元数据 |

**取舍结论**：宁可多一行机器可读的元数据，也不要模糊判定或大量误报。这条取舍原则适用于本规范所有 MUST 条目。

### 3.2 人类可读部分 → 用正文固定小节

正文**必须**包含以下小节（名称固定，便于机器定位）：

```markdown
## Inputs        <!-- 输入契约：无参数 / 参数含义 / 缺省行为 -->
## Outputs       <!-- 输出契约：对话输出 / 文件路径 + 格式 -->
## Failure modes <!-- 失败模式：前置不满足 / 输入非法 / 外部失败 -->
## Side effects  <!-- 副作用：类别 + 是否可逆 -->
## Dependencies  <!-- 依赖：运行时命令 / 外部服务 / 模型要求 -->
```

**豁免**：若某小节内容为空（例如纯只读技能），写「无」而不是删除小节。**小节存在性本身是检查项**，这样机器可以稳定判定「作者是否思考过这个契约」。

### 7.3 级别调整（已确认）

原始版本把 SPEC-040/042 定为 L2，回测时导致样本仓库在 L2 就失败。经裁决，**上调到 L3**，理由：一个只在个人机器上跑（L2）的技能，作者自己就是唯一用户，输入输出契约的收益有限；而一旦要给别人用（L3），契约缺失的代价立刻显现。

调整后样本仓库**通过 L1 与 L2，在 L3 首次失败**，即其「规范符合等级 = L2 可用级」。

这个结论值得单独强调：**一个 25 个已发布技能、数万使用者的公认优秀仓库，在契约维度上只达到「可用级」。** 这不是样本的耻辱，而是生态年轻的证据——输入/输出/失败/副作用/依赖这五类契约在整个生态中都没有被定义过。**流行度不等于成熟度**，这正是本标准要填的空白。

> 术语区分：此处得到的是 **SPEC 规范符合等级**（准入闸门，二值）。阶段 3 的质量模型（QM）另行给出**质量等级**（6 维度评分），二者可以不一致——例如一个技能功能质量极高但从未声明失败模式，QM 的「功能」维度高、「健壮」维度低。

**基准立场（已确认）**：接受标准与现状的差异，**保持门槛不降**。标准若完全贴合现状，就只是"现状描述"而非"改进目标"，失去增量价值。L4/L5 的要求不因样本未达标而下调。

### 7.4 示例技能的自检结果

`evals/fixtures/release-notes` 在 L5 下 **28 项检查、24 项 MUST 全部通过，退出码 0**。
