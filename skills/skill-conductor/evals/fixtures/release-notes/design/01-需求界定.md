# 需求界定

> STEP-01 中间产物（示例技能的完整流程产物）

## 失败模式

- 具体坏结果：每次发版前要手工翻 `git log` 和 GitHub PR 列表，把几百条提交标题抄进 CHANGELOG。
  真实发生过的坏结果有两次：一次漏掉了一个 breaking change 的 PR，导致下游用户升级后报错；
  一次把内部重构（`chore:`）也写进了发布说明，用户误以为有功能变化。
- 发生频率：每个版本一次（约每两周），漏项时代价高（下游报错、需要发补丁版本）。
- 现有替代方案为何不够：靠人工 checklist，但发版时经常赶时间，checklist 被跳过；
  GitHub 自动生成的 release notes 按提交而非按 PR 分类，且不区分内部改动。

## 触发场景

- 当准备发布一个新版本、需要写 CHANGELOG 条目时
- 当有人问「这一版到底改了什么」时
- 当需要给下游用户一份可读的变更摘要时

## 不做的事

- 不负责创建 git tag 或推送（这是发布流程，不是文档流程）
- 不负责判断某个改动是否值得发布
- 不负责改写 PR 标题（改写会引入未经证实的语义）
- 明确不支持：把未合并的 PR 或草稿 PR 纳入发布说明

## 与现有技能的关系

- 已存在且重叠的技能：无。仓库内的 `code-review` 面向代码质量，`to-tickets` 面向任务拆分，
  都不产出面向用户的发布说明。
- 本技能与它们的分工：本技能只做「已合并 PR → 分类发布说明」这一段转换。
